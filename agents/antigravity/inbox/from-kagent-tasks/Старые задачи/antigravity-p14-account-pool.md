**Исполнитель: Antigravity**

# P14 — пул аккаунтов поставщиков с ротацией и ручным управлением

Правила — `AGENTS.md`. Ветка `wt/p14-account-pool` от свежего `origin/main`.

## Режим исполнения

Antigravity может делегировать субагентам: состояния и переходы аккаунта, аренду при
параллельных запросах, учёт расхода по аккаунтам. За оркестратором остаются: модель
конфигурации, поведение при исчерпании пула и прогон сквозных сценариев на совмещённой
ветке. Субагент, написавший механизм аренды, не проверяет его сам.

## Проблема

У поставщика в `ModelRegistry` сейчас **один** набор учётных данных: `set_provider(name,
endpoint, api_key)`. У владельца несколько аккаунтов на каждом поставщике, и когда лимит
одного заканчивается, работа встаёт, хотя остальные свободны.

Дополнительно: оркестратор и субагенты работают одновременно. Если сделать «активный
аккаунт», который переключается целиком, все параллельные задачи уйдут в один аккаунт и
выжгут его в несколько раз быстрее, а остальные будут простаивать. Поэтому нужно не
переключение, а распределение: аккаунт выбирается **на каждый запрос**.

## Что сделать

### 1. Пул вместо ключа

Конфигурация описывает аккаунты и пулы, роли привязываются к пулам:

```yaml
providers:
  opencode-go:
    endpoint: ...
    accounts: [oc-1, oc-2, oc-3, oc-4]
  nvidia:
    endpoint: ...
    accounts: [nv-1, nv-2, nv-3, nv-4]
  codex:
    accounts: [cx-1, cx-2, cx-3]

pools:
  orchestrator: [cx-1, cx-2, cx-3]
  subagents:    [oc-1, oc-2, oc-3, oc-4, nv-1, nv-2, nv-3, nv-4]
```

Учётные данные аккаунтов берутся из окружения или файла секретов, **в конфигурации в
открытом виде их нет**. Имена переменных объявляются, значения — нет.

### 2. Состояние аккаунта

`available` → `throttled` (лимит, известно время сброса) → `exhausted` (квота исчерпана до
конца периода) → `failed` (отказ авторизации, истёкший токен). Отдельно `disabled` —
выключен человеком.

Переход в `throttled` происходит **по ответу поставщика**: код 429 и заголовок времени
сброса, а не по нашему счётчику запросов. Считать лимит самостоятельно бесполезно: у
поставщиков он устроен по-разному, и наша оценка будет расходиться с их.

Если поставщик не сообщил время сброса, применяется объявленная в конфигурации отсрочка по
умолчанию, и это видно в состоянии.

### 3. Выбор с арендой

- аккаунт выбирается на каждый запрос из пула роли и берётся в аренду на время вызова;
- два параллельных запроса не получают один аккаунт;
- аренда снимается по завершении, включая ошибку и таймаут — утечка аренды выводит аккаунт
  из оборота навсегда, это недопустимо;
- порядок выбора объявлен: наименее недавно использованный из доступных. Случайный выбор не
  годится, он даёт неравномерность на малых пулах;
- при `429` аккаунт помечается, запрос уходит на следующий свободный, попытка пишется в
  телеметрию. Это не «повтор», а смена аккаунта — в записи должно быть видно различие.

### 4. Исчерпание пула

Если свободных аккаунтов нет, запрос **завершается явной ошибкой** с указанием, когда
освободится ближайший. Не ждать бесконечно, не уходить в другой пул, не деградировать молча.

Ожидание допустимо, если оно объявлено в конфигурации и ограничено сверху.

### 5. Ручное управление

Три действия через API:

- **закрепить** роль за конкретным аккаунтом;
- **отключить** аккаунт;
- **сбросить** пометку `throttled` вручную.

Закрепление отменяет автоматический выбор. Если закреплённый аккаунт исчерпан, запрос падает
с явной ошибкой и **не уходит на другой**. Тихая подмена того, что человек закрепил руками,
— худшее поведение из возможных: владелец считает, что работает на одном аккаунте, а
работает на другом.

### 6. Состояние наружу

Маршрут только на чтение: список аккаунтов, состояние каждого, время сброса, число запросов
и расход за период, признак закрепления. Он понадобится экрану управления, который делается
отдельной задачей.

Секреты в ответе не появляются ни в каком виде, включая частично замаскированные.

### 7. Связь с действующими решениями

- **секреты не пересекают границу песочницы** — пул живёт на стороне хоста, ключ не попадает
  ни в контекст модели, ни в рантайм, ни в логи, ни в текст ошибки (`AGENTS.md` §9,
  ADR-0017);
- **расход считается по аккаунтам** — иначе стоимость успешной задачи перестанет сходиться,
  когда работа размазана по восьми аккаунтам. Добавить измерение «аккаунт» в учёт
  (ADR-0006);
- **кассета записывает, каким аккаунтом сделан вызов** — иначе воспроизведение прогона
  неполно (ADR-0004). В режиме `replay` аккаунт не выбирается вообще.

### 8. Решение зафиксировать

Новый ADR со статусом `proposed`, следующий свободный номер: пул вместо активного аккаунта,
аренда, поведение при исчерпании, приоритет ручного закрепления.

## Тесты

- 429 с временем сброса переводит аккаунт в `throttled` и уводит запрос на следующий;
- 429 без времени сброса применяет отсрочку по умолчанию;
- десять параллельных запросов на пуле из четырёх аккаунтов распределяются, а не идут в один;
- аренда снимается при ошибке и при таймауте;
- исчерпанный пул даёт явную ошибку, а не ожидание и не переход в чужой пул;
- закреплённый исчерпанный аккаунт даёт ошибку и не подменяется;
- отключённый аккаунт не выбирается;
- секрет не появляется в ответе маршрута состояния, в логах и в тексте ошибки — проверяется
  поиском по выводу;
- в режиме `replay` обращения к пулу не происходит.

Ни один тест не обращается к настоящему поставщику: искусственный адаптер, как в ADR-0004.

## Чего не делать

- экран управления аккаунтами в Web — отдельная задача после этой;
- автоматическое определение остатка квоты опросом поставщика: пока только то, что он сам
  сообщил в ответе;
- перенос ключей между аккаунтами, импорт из чужих инструментов, работа с файлами учётных
  данных сторонних IDE.


- параллельная нагрузка распределяется — показать выводом теста;
- ручное закрепление, отключение и сброс работают через API;
- закреплённый аккаунт не подменяется автоматически;
- секретов нет ни в одном выводе;
- ADR добавлен со статусом `proposed`;
- `CHANGELOG.md` обновлён;
- ссылка на зелёный прогон.
