# P3 — git-контур и контракт задачи

Правила работы — `AGENTS.md` в корне репозитория.
Репозиторий: `https://github.com/ochenstarik-ui/kagent`, база — свежий `main`.
Ветка: новая от `origin/main`, `wt/d3-git-contour`.

**Предусловие: задачи P1 и P2 приняты и влиты.** Без настоящей генерации кода git-контуру
нечего фиксировать.

## Проблема

Во всём репозитории **ноль git-операций**: поиск по `git clone`, `worktree`, `git commit`,
`create_pull_request` не находит ничего ни в одном сервисе. Результат работы агента остаётся
во временном каталоге и никуда не попадает.

Раздел 8.2 ТЗ требует для каждой задачи отдельный worktree, отдельную ветку и запрет работы
в основной ветке пользователя. Раздел 8.3 требует машиночитаемый контракт задачи с
разрешёнными путями, действиями и лимитами. Ничего из этого не реализовано.

## Что сделать

### 1. Контракт задачи

Реализовать разбор и применение контракта из раздела 8.3 ТЗ: `allowed_paths`,
`forbidden_paths`, `allowed_actions`, `approval_required`, `limits` (время, стоимость, число
изменённых файлов, число ходов, число repair-циклов).

Контракт создаётся до запуска и **неизменяем во время выполнения**. Попытка выйти за него —
отказ шага с указанием нарушенного пункта, а не предупреждение.

### 2. Рабочее пространство

Для задачи разработки:

- отдельный клон или worktree репозитория проекта;
- отдельная ветка с детерминированным именем от идентификатора задачи;
- запрет работы в базовой ветке — проверяется до первого изменения;
- отдельный каталог артефактов;
- удаление рабочего пространства после завершения, с сохранением артефактов.

Ссылка на репозиторий берётся из поля `repositoryUrl` проекта, которое уже есть в схеме и
до сих пор нигде не используется.

### 3. Фиксация изменений

- атомарные коммиты с идентификаторами задачи и запуска в trailers, как требует ADR-0009;
- перед завершением — обновление ветки относительно базовой; верификация на устаревшей базе
  не даёт права на слияние;
- проверка, что изменённые пути входят в `allowed_paths`; нарушение отменяет фиксацию;
- запрет `push --force`, переписывания истории и обхода hook'ов для агентских идентичностей.

### 4. Pull request

Создание pull request с описанием: постановка, что изменено, вывод проверок, использованные
модели и стоимость. Разделять в описании изменения кода и изменения тестов — требование
ADR-0005.

Учётные данные доступа к репозиторию **не хранятся в коде и не попадают в контекст модели**.
Токен передаётся рантайму как секрет с ограниченным сроком и маскируется в логах.

### 5. Идемпотентность

Создание ветки, коммита и pull request — внешние эффекты. При повторе шага после потери
связи они не должны выполняться дважды. Реализовать ключ идемпотентности из ADR-0010 хотя бы
в минимальном виде: журнал выполненных эффектов с ключом и внешним идентификатором, повтор
возвращает сохранённый результат.

Это не полный effect ledger из этапа 0.9.4, а его частный случай для git-операций. Отметить
это в отчёте.

### 6. Тесты

Против локального временного репозитория, без сети и без GitHub:

- ветка создаётся, базовая ветка не изменяется;
- изменение вне `allowed_paths` отклоняется до коммита;
- коммит содержит идентификаторы в trailers;
- повтор шага не создаёт вторую ветку и второй коммит;
- работа в базовой ветке отклоняется;
- рабочее пространство удаляется, артефакты сохраняются.

Создание pull request проверяется на заглушке клиента: настоящий вызов GitHub в тестах
запрещён.

## Критерий приёмки

```bash
ruff check services scripts
python -m pytest tests/unit -q
python scripts/drift_check.py
```

- сквозной прогон в режиме `replay`: задача с контрактом проходит план, разработку,
  проверки, коммит в отдельную ветку и подготовку pull request на локальном репозитории.
  Вывод приложить;
- ни один тест не ходит в сеть;
- секреты не появляются в логах и артефактах — проверить поиском по выводу прогона;
- возможность в `docs/capabilities.json` со ссылкой на job как доказательство;
- ссылка на зелёный прогон приложена.

## После этой задачи

Замыкается путь «постановка → план → код → проверки → ветка → pull request». Это первая
точка, в которой продукт делает то, ради чего задуман. До неё платформа остаётся
инфраструктурой.
