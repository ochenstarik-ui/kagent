**Исполнитель: Antigravity**

# P12 — сделать Web-клиент разворачиваемым и рабочим

Правила — `AGENTS.md`. Ветка `wt/p12-web-deployable` от свежего `origin/main`.

## Режим исполнения

Antigravity может делегировать субагентам: сборку контейнера, маршруты и заголовки на
Gateway, экраны интерфейса. За оркестратором остаются: единый контракт данных между Web и
Control Plane, объединение изменений и сквозной сценарий на собранном образе. Отчёт субагента
про «страница открывается» без прогона против поднятого compose не принимается.

## Проблема

Web-клиент существует в `apps/web`, но **развернуть его невозможно**: в
`docker-compose.yml` нет ни одной записи о нём, `apps/web/Dockerfile` отсутствует.

Управлять платформой сегодня можно только через `curl`. Панель, ради которой писался
дашборд, недоступна ни в одном сценарии установки. Раздел 20 ТЗ описывает главный экран,
экран проекта, timeline и approvals — из этого не разворачивается ничего.

Отдельно: страницы ходят в `/api/control-plane/...` и `/api/observability/...`. Маршрут к
observability на Gateway уже добавлен, но `next.config` с переписыванием путей в репозитории
нет — значит в разработке эти запросы попадают в сам Next.js и возвращают 404.

## Что сделать

### 1. Контейнер

`apps/web/Dockerfile` с многоступенчатой сборкой: установка зависимостей, сборка Next.js,
запуск в режиме production. Образ не должен содержать исходники и dev-зависимости.

Проверить, что сборка проходит в CI, а не только локально.

### 2. Запись в compose

Web добавляется в `docker-compose.yml` и **не публикует свой порт напрямую**: трафик идёт
через Gateway, как для остальных сервисов. Периметр, закрытый в PR #15, не ослабляется.

Зависимость от Gateway по состоянию работоспособности. Адрес Gateway передаётся переменной
окружения, а не зашивается.

### 3. Маршруты

Настроить переписывание путей так, чтобы `/api/control-plane/*` и `/api/observability/*`
работали одинаково в разработке и в собранном образе. Дублировать список маршрутов в двух
местах нельзя — один источник.

### 4. Рабочий сценарий, а не заглушка

Сейчас дашборд показывает статус сервисов и список проектов. Довести до состояния, в котором
им можно пользоваться:

- вход по паролю и второму фактору, если он включён;
- список проектов, создание проекта;
- список задач проекта, создание задачи;
- страница запуска: шаги, статусы, использованные модели, токены и стоимость, ссылки на
  артефакты;
- видимый статус «требуется решение человека» — тот самый, что выставляет pipeline при
  исчерпании repair-циклов. Если оператор не видит его в интерфейсе, механизм бесполезен.

Ошибки показываются человеку, а не тонут в консоли.

### 5. Проверки

- модульные тесты компонентов, которые разбирают ответы API;
- сквозной сценарий против поднятого compose: регистрация, вход, создание проекта, создание
  задачи, появление запуска в интерфейсе. Запускается в CI отдельным job, использует уже
  существующий сервисный контейнер PostgreSQL.

## Чего не делать

- не менять контракт API ради удобства интерфейса: расхождение — повод для отдельной задачи;
- не публиковать порт Web наружу в обход Gateway;
- не реализовывать Workflow Canvas и Session Tree из разделов 20.3 и 43.7 — это отдельный
  объём.

## Критерий приёмки

```bash
pnpm --filter @kagent/web typecheck
pnpm --filter @kagent/web build
pnpm build
docker compose config -q
```

- образ Web собирается в CI;
- `docker compose up -d` поднимает Web, и он доступен через Gateway — показать запросом;
- сквозной сценарий проходит в CI;
- ни один внутренний порт не опубликован;
- ссылка на зелёный прогон приложена.
