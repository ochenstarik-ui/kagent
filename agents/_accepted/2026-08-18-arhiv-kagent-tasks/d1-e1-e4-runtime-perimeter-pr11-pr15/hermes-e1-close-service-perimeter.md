# E1 — закрыть периметр внутренних сервисов

Правила работы — `AGENTS.md` в корне репозитория.
Репозиторий: `https://github.com/ochenstarik-ui/kagent`, база — свежий `main`.
Ветка: новая от `origin/main`, `wt/e1-service-perimeter`.

**Зависимостей нет.** Не пересекается с задачами P по файлам, кроме `docker-compose.yml`.

## Проблема

`services/agent-runtime` выполняет произвольные команды оболочки через
`asyncio.create_subprocess_shell`. При этом в `docker-compose.yml` его порт, как и порты
reasoning-engine, pipeline и observability, публикуется наружу:

```yaml
ports:
  - "${RUNTIME_PORT:-8300}:8300"
```

Аутентификации на этих сервисах нет никакой. Любой, кто дотянется до порта, выполняет команды
в контейнере. Публикация без привязки к адресу означает все интерфейсы хоста.

Это уже плохо, а после задач P2 и P3 станет хуже: рантайм получит доступ к репозиторию и
токену для pull request.

Раздел 5 `docs/ARCHITECTURE.md` прямо требует: внешний трафик завершается на Gateway,
внутренние сервисы по умолчанию не доступны публично, порты привязаны к петлевому интерфейсу.
Сейчас это нарушено.

## Что сделать

### 1. Убрать публикацию портов

Внутренние сервисы — reasoning-engine, agent-runtime, pipeline, observability — не публикуют
порты на хост. Они доступны только по внутренней сети compose.

Наружу остаётся Gateway. Инфраструктурные порты PostgreSQL, NATS и MinIO уже привязаны к
`127.0.0.1` — это сохранить.

Для отладки допустим отдельный override-файл, не включённый по умолчанию. В основном файле
публикации быть не должно.

### 2. Служебная аутентификация

Внутренние вызовы между сервисами подписываются общим служебным секретом:

- значение из переменной окружения, разное для каждой установки;
- отсутствие или несовпадение — `401`, запрос не выполняется;
- секрет не логируется и не попадает в текст ошибки;
- проверка обязательна на agent-runtime и pipeline: именно они выполняют действия;
- на `/health/live` и `/health/ready` проверка не распространяется, иначе сломается
  healthcheck compose.

Реализация простая и без новых зависимостей: заголовок с секретом и сравнение постоянного
времени. Полноценные mTLS и сервисные идентичности — отдельный этап, здесь не нужны.

### 3. Маршруты Gateway

Gateway знает только про control-plane и reasoning. Web-клиент при этом ходит в
`/api/observability/...`, которого нет в таблице маршрутов. Добавить маршрут к
observability, чтобы панель получала данные, не требуя публикации порта.

### 4. Документация

Обновить `.env.example` новой переменной и `docs/DEPLOYMENT.md` — в разделе про безопасность
сейчас сказано «configure firewall: only expose Gateway port 8080», хотя compose публикует
пять портов. Привести в соответствие.

## Тесты

- запрос к рантайму без служебного секрета получает `401`;
- запрос с неверным секретом получает `401`;
- запрос с верным секретом выполняется;
- `/health/live` отвечает без секрета;
- `docker compose config` разбирается и не содержит публикаций внутренних портов — проверить
  разбором файла, а не глазами.

## Критерий приёмки

```bash
ruff check services scripts
python -m pytest tests/unit -q
docker compose config -q
python scripts/drift_check.py
```

Последняя команда требует Docker; если его нет в окружении исполнителя, разобрать
`docker-compose.yml` как YAML и проверить отсутствие ключа `ports` у внутренних сервисов —
и сказать в отчёте, что полная проверка не выполнялась.

Ссылка на зелёный прогон приложена.

## Границы

`docker-compose.yml`, внутренние сервисы в части проверки секрета, `services/gateway`,

решение ADR-0017.
