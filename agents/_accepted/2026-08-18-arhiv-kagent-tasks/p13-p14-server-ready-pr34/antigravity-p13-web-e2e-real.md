# P13 — довести Web до проверяемого сценария

Правила — `AGENTS.md`. Ветка `wt/p13-web-e2e-real` от свежего `origin/main`.

## Режим исполнения

Antigravity может делегировать субагентам: подключение Playwright к CI, экраны входа и
проекта, страницу запуска. За оркестратором остаются: единый сценарий, порядок ожидания
готовности сервисов и прогон сквозного теста на собранном образе. Субагент, сделавший экран,
не проверяет свой же экран.

## Что уже сделано в P12

Приняты и влиты: `apps/web/Dockerfile`, запись в compose через Gateway без публикации порта,
переписывание маршрутов, разбор ответов API с модульными тестами. Это работало и это
осталось.

## Проблема

Две вещи из постановки P12 не сделаны, и обе относятся к доказательству.

**Playwright добавлен, но не запускается.** В `.github/workflows/ci.yml` нет ни одного
упоминания Playwright или e2e. Установлена зависимость, написан конфиг, создан спек — и всё
это не выполняется ни в одном прогоне. Тот же дефект, который проверка дрейфа создана
ловить: артефакт есть, достижимости нет.

**Сценарий подменён проверкой заголовка.** Весь сквозной тест выглядит так:

```ts
test('dashboard loads', async ({ page }) => {
  await page.goto('/');
  await expect(page.locator('text=Панель управления')).toBeVisible();
});
```

Он подтверждает, что страница отрисовалась. Постановка требовала другого: вход, создание
проекта, создание задачи, видимый запуск. Проверка заголовка не отличит рабочую панель от
панели, у которой сломаны все запросы к API.

## Что сделать

### 1. Подключить к CI

Отдельный job: поднимает compose, ждёт готовности по healthcheck контейнеров, выполняет
Playwright против Gateway, сохраняет отчёт и трассировки упавших сценариев как артефакт.

Без артефактов разбор падения в CI превращается в гадание.

### 2. Настоящий сценарий

Один сквозной путь, каждый шаг проверяется по видимому результату, а не по коду ответа:

- регистрация нового пользователя;
- вход, попадание на панель;
- создание проекта, он появляется в списке;
- создание задачи в проекте, она появляется в списке задач;
- открытие запуска: видны шаги, статусы, использованная модель, токены и стоимость;
- видимый статус «требуется решение человека», если запуск в него пришёл.

Данные для каждого прогона уникальны, чтобы тест не зависел от порядка и от остатков
предыдущего запуска.

### 3. Негативные проверки

Без них сценарий доказывает только счастливый путь:

- вход с неверным паролем не пускает и показывает ошибку человеку;
- создание задачи в несуществующем проекте не роняет интерфейс;
- недоступность control-plane показывается пользователю, а не молчаливой пустой страницей.

### 4. Показать, что тест ловит

Сломать один запрос в интерфейсе, показать красный прогон, откатить. Вывод приложить.
Иначе неизвестно, проверяет ли сценарий что-нибудь.

## Чего не делать

- не менять контракт API ради удобства интерфейса;
- не публиковать порт Web в обход Gateway;
- Workflow Canvas и Session Tree — отдельный объём.

## Критерий приёмки

```bash
pnpm --filter @kagent/web typecheck
pnpm --filter @kagent/web build
docker compose config -q
```

- job с Playwright зелёный и выполняет весь сценарий;
- отчёт и трассировки сохраняются как артефакт прогона;
- демонстрация со сломанным запросом приложена;
- негативные проверки проходят;
- ссылка на зелёный прогон.
