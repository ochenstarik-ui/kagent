# E7 — сделать подтверждённый статус видимым в репозитории

Правила — `AGENTS.md`. Ветка `wt/e7-visible-verified-status` от свежего `origin/main`.

## Режим исполнения

Hermes может делегировать субагентам разбор источников доказательств, правку генератора и
тесты. За собой оркестратор оставляет: выбор схемы хранения подтверждений, объединение
изменений и полный прогон критерия приёмки на итоговой ветке. Отчёт субагента не заменяет
diff и зелёный CI.

## Проблема

PR #14 подал результаты job'ов в вычисляемый статус, и механизм работает. Но
**закоммиченный `docs/ROADMAP.md` по-прежнему показывает `unverified` для всех 32 из 32
возможностей** — проверено на текущем `main`:

```
grep -oE "\b(un)?verified\b" docs/ROADMAP.md | sort | uniq -c
     32 unverified
```

Причина: job `measurability` генерирует подтверждённую версию, публикует её как артефакт
прогона и на этом останавливается. В репозитории остаётся детерминированный вариант без
доказательств, потому что его защищает guard, сравнивающий с генерацией `--no-run-commands`.

Итог: доказательства собираются, но увидеть их можно только скачав артефакт конкретного
прогона. Тот, кто открывает репозиторий, видит «ничего не подтверждено» — ровно ту картину,
против которой написан ADR-0016.

## Что сделать

Выбрать и обосновать одну из схем, не ломая защиту от ручной правки:

**Схема А — отдельный файл состояния.** `docs/ROADMAP.md` остаётся детерминированным и
защищённым, а рядом ведётся `docs/roadmap-status.md` либо `docs/verification-state.json`,
который обновляется автоматически после успешного прогона на `main` и содержит: возможность,
статус, ссылку на прогон, коммит, время. Ручная правка этого файла роняет сборку так же, как
сейчас роняет правка roadmap.

**Схема Б — подтверждения как вход генерации.** Результаты прогонов `main` складываются в
трекаемый файл, генератор берёт их как источник, и `ROADMAP.md` становится подтверждённым
детерминированно: одинаковый вход даёт одинаковый выход, guard продолжает работать.

Схема Б предпочтительнее: один файл вместо двух и никакого расхождения между «настоящим» и
«показанным» статусом. Если выберешь А — обоснуй в отчёте.

Требования, общие для обеих схем:

- обновление подтверждений происходит **только по прогону на `main`**, не по прогону ветки:
  иначе любая ветка сможет объявить возможность подтверждённой;
- отсутствие результата по-прежнему означает `unverified`;
- зелёный job засчитывается только тем возможностям, которые на него ссылаются;
- в записи сохраняются ссылка на прогон и коммит — доказательство должно быть проверяемым
  третьей стороной, а не словом генератора;
- защита от ручной правки сохраняется и проверяется демонстрацией.

## Показать, что работает

В отчёте привести:

- фрагмент видимого статуса с возможностями `verified` и ссылками на прогон;
- сколько возможностей подтверждено, сколько частично, сколько без доказательств — картина
  должна быть неровной. Если после задачи подтверждено всё, значит доказательства
  засчитываются слишком щедро, и это дефект, а не успех;
- демонстрацию: ручная правка статуса роняет сборку.

## Чего не делать

- не менять состав доказательств в `docs/capabilities.json`, чтобы улучшить картину;
- не засчитывать прогон ветки как подтверждение;
- не наполнять eval-случаи.

## Критерий приёмки

```bash
python -m pytest tests/unit -q
python scripts/roadmap_status.py --check --no-run-commands
python scripts/drift_check.py
```

- в репозитории видно хотя бы одну подтверждённую возможность со ссылкой на прогон `main`;
- возможности без доказательств остались `unverified`;
- ручная правка роняет сборку — демонстрация приложена;
- модульные тесты покрывают: подтверждение по прогону `main`, отказ засчитывать прогон
  ветки, отсутствие результата даёт `unverified`;
- ссылка на зелёный прогон приложена.
