# P1 — настоящий вызов модели в Reasoning Engine

Правила работы — `AGENTS.md` в корне репозитория.
Репозиторий: `https://github.com/ochenstarik-ui/kagent`, база — свежий `main`.
Ветка: новая от `origin/main`, `wt/d1-real-model-execution`.
Первая из трёх задач продуктовой вертикали P. Выполняется до P2.

## Проблема

`/v1/execute` в `services/reasoning-engine/src/server.py` — заглушка. Дословно из кода:

```python
# Simulated execute — in real impl, look up the prior decision
execution = engine.telemetry[-1] if engine.telemetry else None
```

Он возвращает последнюю запись телеметрии независимо от `request_id` и `messages`, то есть
модель не вызывается **ни разу за весь жизненный цикл платформы**. Метод `engine.execute()`
в `src/engine.py` написан, но из маршрутов не вызывается.

Следствие: маршрутизация по способностям выбирает модель, а выбранная модель ничего не
делает. Вся заявленная функция продукта опирается на этот вызов.

## Что сделать

### 1. Хранение решения

`/v1/decide` возвращает `request_id`, но само решение нигде не сохраняется. Завести
хранилище решений с ограниченным временем жизни: `request_id` → выбранная модель, запасные
модели, ограничения запроса, оценка стоимости, время создания.

`/v1/execute` принимает `request_id`, находит решение и выполняет **его**, а не последнее
попавшееся. Неизвестный или истёкший `request_id` — ошибка 404 с явным текстом, а не тихая
подстановка.

### 2. Настоящее выполнение

Вызывать `engine.execute()` с сообщениями из запроса. Требования:

- таймаут на вызов и корректная отмена;
- при ошибке провайдера — переход к запасной модели из решения, с записью попытки;
- исчерпание запасных вариантов возвращает ошибку, а не успешный ответ с пустым содержимым;
- учёт токенов и стоимости по фактическому ответу провайдера, а не по оценке;
- запись в телеметрию каждой попытки, включая неудачные;
- секреты провайдера не попадают ни в ответ, ни в логи, ни в текст ошибки.

### 3. Ответ

`ExecuteResponse` должен содержать содержимое ответа модели. Сейчас в нём только метрики —
вызывающая сторона не может получить результат работы, ради которого всё делается.
Расширение аддитивное, форма существующих полей не меняется.

### 4. Кассеты и режимы

Реализовать режимы из ADR-0004 в объёме, достаточном для тестов:

- `live` — обычный вызов провайдера;
- `record` — вызов с записью запроса и ответа;
- `replay` — ответ берётся из записи, обращение к провайдеру запрещено.

Режим — из переменной окружения, по умолчанию `live`. Отсутствие записи в режиме `replay` —
жёсткая ошибка, а не переход к живому вызову. Хранилище записей — файлы на диске, объектное
хранилище подключается отдельной задачей.

### 5. Тесты

**Ни один тест не обращается к настоящему провайдеру и не тратит токены** — правило из
ADR-0004. Использовать искусственный провайдер, удовлетворяющий тому же контракту адаптера.

Покрыть: успешный вызов; переход к запасной модели при ошибке первой; исчерпание запасных;
таймаут; неизвестный `request_id`; подсчёт стоимости по фактическим токенам; режим `replay`
без обращения к сети; отсутствие записи в `replay` роняет запрос.

## Чего не делать

- не подключать pipeline к этому маршруту — это задача P2;
- не реализовывать бюджетный ledger из ADR-0006, кэш из ADR-0013 и объектное хранилище
  кассет: здесь только файлы и учёт по факту;
- не добавлять новых поставщиков моделей и не трогать ключи.

## Критерий приёмки

```bash
ruff check services scripts
python -m pytest tests/unit -q
python scripts/drift_check.py
```

- `/v1/execute` выполняет решение по `request_id` и возвращает содержимое ответа;
- ни один тест не требует ключа провайдера — проверяется запуском с пустым окружением;
- прогон в режиме `replay` воспроизводит записанный ответ побайтово;
- возможность в `docs/capabilities.json` ссылается на имя job как на доказательство;
- ссылка на зелёный прогон приложена.
