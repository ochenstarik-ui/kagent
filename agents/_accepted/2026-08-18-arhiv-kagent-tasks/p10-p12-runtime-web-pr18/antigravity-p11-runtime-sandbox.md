**Исполнитель: Antigravity**

# P11 — обязательная песочница для Agent Runtime

Правила — `AGENTS.md`. Ветка `wt/p11-runtime-sandbox` от свежего `origin/main`.

**Предусловие: P8, P9 и P10 приняты и влиты.** До них рантайм исполняет шаблоны, и защищать
особо нечего. После них он исполняет код, написанный моделью, и работает с репозиторием и
токеном для pull request — с этого момента отсутствие песочницы становится главным риском
продукта.

## Режим исполнения

Antigravity может делегировать субагентам: профиль изоляции контейнера, лимиты ресурсов,
тесты выхода из песочницы. За оркестратором остаются: выбор механизма изоляции, интеграция с
`AgentRuntime`, проверка того, что тесты действительно ловят побег, и полный прогон на
объединённой ветке. Отчёт субагента про «изоляция работает» без падающего негативного теста
не принимается.

## Проблема

`services/agent_runtime` исполняет произвольные команды через `create_subprocess_shell` от
пользователя контейнера, с правами на весь его файловый доступ. Периметр закрыт (PR #15):
порт не публикуется, вызовы требуют служебный секрет. Это защищает от постороннего, но не от
того, что выполняется **внутри**: недоверенный репозиторий, инструкция из задачи, ответ
модели.

ТЗ, раздел 42.6, и ADR-0017 называют песочницу блокирующим условием, а не улучшением:
программная среда агента не включается без неё ни в одном режиме, включая локальную
разработку. Раздел 15.5 перечисляет минимальные требования.

Пока её нет, установка KAgent на сервер с публичным адресом небезопасна независимо от того,
насколько хорош остальной код.

## Что сделать

### 1. Профиль изоляции

Исполнение инструментов рантайма происходит внутри изолированного окружения:

- rootless-контейнер либо microVM, процесс не от root;
- отдельный UID для каждой задачи;
- namespaces: PID, mount, network;
- seccomp-профиль, ограничивающий системные вызовы;
- AppArmor или SELinux там, где доступны;
- корневая файловая система только для чтения;
- рабочий каталог задачи — единственное место с правом записи, уничтожается после
  завершения;
- лимиты CPU, памяти, числа процессов и места на диске;
- сеть запрещена по умолчанию; доступ выдаётся адресно под конкретный шаг.

Механизм выбрать самостоятельно и обосновать: контейнер в контейнере, отдельный
непривилегированный исполнитель или microVM. Требование одно — он должен работать в Docker
Compose на обычном сервере Linux без привилегированного режима.

### 2. Отказ вместо тихой деградации

Если изоляция недоступна в текущем окружении, рантайм **не запускает инструменты вообще** и
возвращает ошибку с указанием причины. Флага «работать без песочницы» не существует.

Это ровно тот пункт, который отличает настоящее требование от пожелания.

### 3. Секреты

Токен репозитория и ключи провайдера не попадают внутрь песочницы. Операции, которым они
нужны, выполняет хост по типизированному запросу — граница из ADR-0017. Внутри доступны
только данные задачи.

### 4. Негативные тесты

Главная часть задачи. Проверка обязана падать, если изоляция сломана:

- чтение файла вне рабочего каталога отклоняется;
- запись вне рабочего каталога отклоняется;
- запись в корневую файловую систему отклоняется;
- сетевое соединение из шага без выданного доступа не устанавливается;
- превышение лимита памяти и числа процессов останавливает шаг, а не хост;
- переменные окружения хоста, включая токены, внутри недоступны;
- после завершения задачи рабочий каталог удалён, процессы не остались.

Каждый тест сначала показывается **красным на версии без песочницы** — иначе неизвестно,
проверяет ли он что-нибудь. Вывод обоих состояний привести в отчёте.

### 5. Документация

- ADR на выбранный механизм со статусом `proposed`, следующий свободный номер;
- раздел в `docs/DEPLOYMENT.md`: требования к хосту, что будет, если они не выполнены;
- обновить `docs/THREAT_MODEL.md`: пункт «Arbitrary host command execution» перестаёт быть
  «later allowlisted sandbox tools».

## Чего не делать

- не реализовывать программную среду с единственным инструментом из ADR-0017: здесь только
  песочница как предусловие;
- не менять модель разрешений инструментов;
- не трогать периметр из PR #15.

## Критерий приёмки

```bash
ruff check services scripts
python -m pytest services tests -q
python scripts/drift_check.py
docker compose config -q
```

- все негативные тесты проходят с песочницей и падают без неё — показано выводом;
- при недоступной изоляции рантайм отказывается исполнять инструменты, а не работает
  по-старому;
- прогон в непрерывной интеграции зелёный, песочница проверяется в CI, а не только вручную;
- ADR добавлен со статусом `proposed`;
- ссылка на зелёный прогон приложена.

## Почему это стоит делать раньше остального

Это единственная задача из очереди, после которой можно честно ответить «да» на вопрос
«можно ли поставить на мой сервер». Всё остальное добавляет возможности; эта делает
безопасным их использование.
