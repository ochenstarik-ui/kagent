# E13 — публиковать подтверждённый статус без потока pull request

Правила — `AGENTS.md`. Ветка `wt/e13-verification-state-without-prs` от свежего `origin/main`.

## Режим исполнения

Задача небольшая и делится плохо: одна логика публикации, один job. Делегировать имеет смысл
только уборку накопившихся веток и тесты. Решение о способе публикации остаётся за
оркестратором.

## Проблема

E7 сделала главное: подтверждённый статус возможностей стал виден, а не лежал в артефакте
прогона. Но выбранный способ публикации — создание pull request из CI — даёт побочный
эффект, который быстро перевесит пользу.

Сейчас в репозитории:

```
automation/verification-state-31555740328-1
automation/verification-state-31555740328-2
```

Две ветки **с одного прогона**, плюс открытый PR #28. Каждый пуш в `main` добавляет ветку и
PR. За неделю активной работы это десятки открытых pull request, среди которых перестанут
находиться настоящие.

Отдельно: сама возможность создавать PR из CI пришлось включать настройкой репозитория,
которая разрешает это **всем** рабочим процессам. Чем меньше прав у автоматики, тем лучше.

## Что сделать

### 1. Выбрать способ без pull request

Два разумных варианта, выбрать один и обосновать в отчёте:

- **постоянная ветка состояния.** Файл подтверждений пишется в одну ветку, например
  `verification-state`, принудительным обновлением. Истории накопления нет, PR нет, ветка
  одна и всегда актуальна;
- **коммит в `main` от прогона.** Проще для чтения, но добавляет коммит на каждый пуш и
  требует прав записи в основную ветку у автоматики — этого я бы избегал.

Первый вариант предпочтителен. Если выберешь второй — объясни, чем он лучше в нашем случае.

### 2. Сохранить строгость

Всё, что E7 обеспечила, обязано остаться:

- подтверждения принимаются **только по прогону на `main`**, прогон ветки не засчитывается;
- отсутствие результата означает `unverified`;
- зелёный job засчитывается только тем возможностям, которые на него ссылаются;
- запись содержит ссылку на прогон и коммит;
- защита закоммиченного `ROADMAP.md` от ручной правки продолжает работать.

### 3. Убрать накопившееся

Удалить ветки `automation/verification-state-*` и закрыть открытые pull request, созданные
этим механизмом, с пояснением. Проверить, что новых не появляется.

### 4. Снять лишнее право

После перехода на ветку состояния право `pull-requests: write` у job больше не нужно —
убрать из рабочего процесса. Права должны быть минимальными по факту, а не по привычке.

Отдельно сообщи в отчёте, что настройку репозитория «разрешить Actions создавать pull
request» можно выключить обратно, если её больше ничто не использует. Сам её не трогай —
это действие владельца.

### 5. Тесты

- публикация с прогона ветки не происходит;
- повторный прогон на `main` обновляет ту же ветку, а не создаёт новую;
- содержимое записи включает ссылку на прогон и коммит;
- ручная правка `ROADMAP.md` по-прежнему роняет сборку.

## Критерий приёмки

```bash
python -m pytest tests/unit -q
python scripts/roadmap_status.py --check --no-run-commands
python scripts/drift_check.py
```

- после двух прогонов на `main` в репозитории одна ветка состояния и ноль новых pull request
  — показать выводом;
- права job сокращены;
- старые ветки и PR автоматики убраны;
- ссылка на зелёный прогон.

## Границы

`.github/workflows/ci.yml`, `scripts/roadmap_status.py` в части публикации, тесты. Состав
доказательств в `docs/capabilities.json` не менять.
