# E15 — экономика исполнения: бюджетный ledger и кэш модельных вызовов

Правила — `AGENTS.md`. Шаг 3 программы `hermes-e14-program-deferred-stages.md`.
Реализует ADR-0006 и ADR-0013, закрывает этап 0.9.4.

**Два pull request, не один.** Ledger и кэш — разные механизмы; сдавать вместе нельзя.

## Режим исполнения

Внутри каждого шага Hermes может делегировать субагентам: схему и миграцию, атомарность
резервирования, ключ кэширования. За оркестратором остаются: транзакционная модель, поведение
при исчерпании и нагрузочный прогон на совмещённой ветке.

Субагент, написавший резервирование, **не проверяет его сам**: правильность видна только под
параллельной нагрузкой.

## Почему сейчас

Пул аккаунтов влит (ADR-0032), продакшн-развёртывание подготовлено (ADR-0033), модель
вызывается по-настоящему. Расход стал реальным, и это единственный слой, где его никто не
ограничивает.

Проверил на текущем `main`: миграций шесть, ни одной про бюджет; в reasoning-engine нет ни
резервирования, ни кэша. Есть только `hard_budget_usd` на запрос.

Этого недостаточно по двум причинам, и обе усилились с появлением пула аккаунтов:

- **лимит на задачу не ограничивает сумму.** Сорок параллельных задач уложатся каждая в свой
  лимит и вместе вынесут месячный бюджет за час. С восемью аккаунтами параллелизм только
  вырос;
- **счётчик после вызова некорректен при параллелизме.** Воркеры читают устаревшую сумму,
  все проходят проверку, лимит пробивается по построению.

## Шаг A — двухфазный ledger

### Учёт

- **резерв** перед шагом, который может вызвать модель: атомарно, в базе, а не в процессе —
  сервисов несколько;
- **списание** факта после вызова, возврат неиспользованного остатка;
- **неудачный вызов списывает настоящую стоимость** — она бывает ненулевой;
- **истечение**: резерв связан с арендой шага, осиротевший освобождается фоновым процессом.
  Утёкший резерв навсегда выводит деньги из оборота.

### Иерархия

Организация → проект → задача → шаг. Резерв обязан пройти на всех уровнях; дочерний бюджет
не превышает свободный остаток родителя. Расход субагента атрибутируется родителю и остаётся
различимым по узлу дерева.

### Измерение «аккаунт»

Пул аккаунтов уже есть. Запись ledger обязана содержать аккаунт, которым сделан вызов, —
иначе при восьми аккаунтах невозможно понять, где кончаются деньги.

### Автостоп

Скорость расхода сравнивается с прогнозом на период. Превышение переводит платформу в режим
ограниченного приёма: новые задачи не принимаются, текущие доводятся до контрольной точки и
паркуются. Порождается инцидент, снимается **явным действием оператора**.

Отдельно — глобальная пауза: один переключатель, останавливающий приём новых шагов везде.
Независима от автостопа и от аварийной остановки задачи.

### Тесты шага A

- **главный**: N одновременных резервов на бюджете под N−1 пропускают ровно N−1;
- списание меньше резерва возвращает разницу;
- неудачный вызов списывает ненулевую стоимость;
- осиротевший резерв освобождается;
- резерв, не прошедший на уровне проекта, не проходит и на уровне задачи;
- превышение скорости расхода переводит в ограниченный приём и порождает инцидент;
- снятие ограничения без действия оператора невозможно;
- стоимость успешной задачи считается из журнала, а не восстанавливается из логов.

## Шаг B — кэш модельных вызовов

Выполняется после слияния шага A: учёт попаданий в кэш пишется в тот же журнал.

- **prefix-stable сборка контекста**: неизменяемые элементы первыми, чтобы работало
  кеширование на стороне поставщика;
- **кэш точных ответов** по ключу `(model_id, model_version, prompt_registry_version,
  request_digest, sampling)`. Реестра промптов ещё нет — заложи поле и заполняй пустым до
  шага 6 программы;
- **схлопывание одновременных одинаковых запросов** в один вызов с раздачей результата;
- **отключение там, где разнообразие является целью**: consensus, shadow mode;
- **изоляция по проектам и классам приватности** — записи не разделяются между проектами;
- **попадание видно в отчёте**: запуск не должен выглядеть дешевле, чем он есть.

### Тесты шага B

- одинаковый запрос второй раз не уходит к поставщику;
- изменение версии модели или параметров сэмплирования даёт промах;
- записи одного проекта не видны другому;
- одновременные одинаковые запросы дают один вызов;
- при отключённом кэшировании попаданий нет;
- в отчёте различимы живые вызовы и попадания.
