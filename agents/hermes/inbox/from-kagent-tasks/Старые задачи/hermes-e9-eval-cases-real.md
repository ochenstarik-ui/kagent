# E9 — наполнить набор оценки настоящими случаями

Правила — `AGENTS.md`. Ветка `wt/e9-eval-cases-real` от свежего `origin/main`.

## Режим исполнения

Случаи независимы — это удобно для делегирования: каждому субагенту свой случай, свой
каталог, свой критерий приёмки. За оркестратором остаются: формат контракта случая, единый
способ фиксации снимка, объединение и прогон всего набора на итоговой ветке.

Субагенту, сделавшему случай, **нельзя поручать проверку своего же случая**: критерий должен
падать на заведомо неверном решении, и проверяет это оркестратор.

## Проблема

Набор оценки объявлен и подключён к CI, но все пять случаев — пустышки:

```
64 байта  eval/cases/bugfix_leaky_limiter/base.tar.gz
64 байта  eval/cases/dependency_upgrade_pin/base.tar.gz
64 байта  eval/cases/feature_add_endpoint/base.tar.gz
64 байта  eval/cases/refactor_extract_helper/base.tar.gz
64 байта  eval/cases/security_fix_header/base.tar.gz
```

Это пустые архивы, помеченные `draft` и не засчитываемые — честно, но бесполезно. Метрики
автономности из ADR-0008 — доля задач, закрытых без человека, число repair-циклов, стоимость
успешного изменения — считать не с чего.

Теперь это стало важным: в `main` появилась настоящая вертикаль, которая вызывает модель,
пишет код и делает коммит. Проверить, работает ли она, можно только на задачах с известным
ответом.

## Что сделать

### 1. Формат случая

Зафиксировать и описать: снимок репозитория, контракт задачи, критерий приёмки, ожидаемые
артефакты. Снимок должен быть маленьким и самодостаточным — десятки килобайт, без сети и без
установки зависимостей из интернета во время прогона.

### 2. Три настоящих случая вместо пяти пустых

Лучше три работающих, чем пять объявленных. Оставить:

- **исправление дефекта**: маленький проект с падающим тестом; критерий — тест зелёный,
  остальные не сломаны;
- **добавление возможности**: проект с описанием и приёмочным тестом, которого нет в коде;
  критерий — тест появляется и проходит;
- **исправление безопасности**: отсутствующий заголовок или проверка ввода; критерий — новая
  проверка есть и покрыта тестом.

Остальные два каталога удалить: объявленный и не наполненный случай хуже отсутствующего.

### 3. Критерий обязан уметь падать

Для каждого случая приложить доказательство: заведомо неверное решение (пустой diff и diff,
ломающий соседний тест) **не проходит** критерий. Без этого неизвестно, проверяет ли случай
что-нибудь.

Это то же требование, что и мутационная проверка из ADR-0005, применённое к набору оценки.

### 4. Прогон в replay

Набор выполняется в режиме `replay` из ADR-0004: записанные ответы модели, ни одного
обращения к провайдеру, ни одного потраченного токена. Записи хранятся вместе со случаем.

Живые прогоны в этой задаче не нужны.

### 5. Метрики

`eval_suite.py` по итогам прогона выдаёт: доля пройденных, число repair-циклов, стоимость по
записям, время. Формат — машиночитаемый, чтобы следующая задача могла сравнивать релизы.

## Чего не делать

- не подключать метрики к гейту релиза: сначала нужны данные хотя бы за несколько прогонов;
- не добавлять живые вызовы провайдера в CI;
- не менять продуктовый код, чтобы случай проходил. Если вертикаль не справляется —
  **это результат измерения, а не дефект случая**. Зафиксировать и сообщить.

## Критерий приёмки

```bash
python scripts/eval_suite.py --replay
python -m pytest tests/unit -q
python scripts/drift_check.py
```

- три случая наполнены, `draft` с них снят, пустые каталоги удалены;
- для каждого показано, что заведомо неверное решение критерий не проходит;
- прогон набора не обращается к сети — проверяется запуском с пустым окружением провайдера;
- отчёт содержит метрики по каждому случаю;
- честно указано, сколько случаев вертикаль проходит на текущем `main`. Ноль из трёх — тоже
  результат, и он не является поводом менять случаи;
- ссылка на зелёный прогон приложена.
