# E2 — подать результаты CI в вычисляемый статус

Правила работы — `AGENTS.md` в корне репозитория.
Репозиторий: `https://github.com/ochenstarik-ui/kagent`, база — свежий `main`.
Ветка: новая от `origin/main`, `wt/e2-ci-evidence`.

**Зависимостей нет.** Не пересекается с задачами P и E1.

## Проблема

Механизм вычисляемого статуса построен и подключён к CI, но данных в него не поступает.
Сгенерированный `docs/ROADMAP.md` сейчас выглядит так — целиком, без единого исключения:

```
- [ ] [gateway.rate_limiter] Request rate limiting — unverified
    - cargo test ...: command evidence not executed
    - rust_ci: CI result unavailable for job: rust
```

При этом job `rust` в том же прогоне зелёный, тесты ограничителя частоты существуют и
проходят. Возможность подтверждена фактически и помечена неподтверждённой.

Причина: job `measurability` вызывает генерацию с `--no-run-commands` и без `--ci-results`,
а плечо, подставляющее результаты прогонов, не подключено. Guard сравнивает два одинаково
пустых файла и всегда проходит.

Итог: проверка формально работает, а показывает `unverified` всегда. Такой отчёт перестают
читать через месяц, и мы возвращаемся к тому, с чего начинали, — только теперь с механизмом,
создающим ложное чувство контроля.

## Что сделать

### 1. Собрать результаты job'ов

В рабочем процессе CI собрать заключения всех job'ов текущего прогона в машиночитаемый файл:
имя job, вывод, идентификатор прогона, коммит, время. Использовать данные, доступные внутри
прогона, без обращения к внешнему API с токеном.

Job `measurability` должен выполняться **после** остальных и получать их результаты.

### 2. Подать в генератор

Передать файл в `roadmap_status.py` через существующий параметр `--ci-results`. Возможность,
все доказательства которой подтверждены, получает статус `verified` с указанием прогона и
коммита. Частично подтверждённая — `partial` с перечислением недостающего.

### 3. Сохранить строгость

- отсутствие результата по-прежнему означает `unverified`, а не «наверное, работает»;
- зелёный job засчитывается только тем возможностям, которые на него ссылаются;
- доказательство типа «команда» засчитывается, только если команда действительно выполнялась
  в прогоне, а не объявлена в реестре;
- guard продолжает падать при расхождении сгенерированного и закоммиченного файла.

### 4. Показать, что механизм работает

Недостаточно зелёного прогона. Привести в отчёте:

- фрагмент `ROADMAP.md` с возможностями в статусе `verified` и ссылкой на прогон;
- демонстрацию: временно сломать один тест, показать, что связанная возможность вернулась в
  `unverified` или `partial`, откатить;
- подтверждение, что возможности без доказательств остались `unverified`.

Ожидаемо и правильно, что после этой задачи большая часть возможностей окажется
подтверждённой, а часть — нет. Второе не надо «дотягивать»: это честная картина, и она
показывает, где доказательств нет.

## Чего не делать

- не менять состав доказательств в `docs/capabilities.json`, чтобы улучшить картину;
- не добавлять возможностям доказательства, которых у них нет;
- не наполнять eval-случаи — они по-прежнему черновые.

## Критерий приёмки

```bash
python -m pytest tests/unit -q
python scripts/roadmap_status.py --check --no-run-commands
python scripts/drift_check.py
```

- в CI появился шаг сбора результатов, `measurability` выполняется после остальных job'ов;
- сгенерированный `ROADMAP.md` содержит хотя бы одну возможность `verified` со ссылкой на
  прогон;
- демонстрация со сломанным тестом приведена;
- модульные тесты покрывают: подтверждение при зелёном job, `unverified` при отсутствии
  результата, `partial` при частичном подтверждении;
- ссылка на зелёный прогон приложена.
