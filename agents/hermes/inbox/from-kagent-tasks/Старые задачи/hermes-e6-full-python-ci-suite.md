# E6 — перевести Python-проверку на полный набор тестов

Правила — `AGENTS.md`. Ветка `wt/e6-full-python-ci-suite` от свежего `origin/main`.

**Предусловия нет.** Прежняя зависимость от E5 снята: блокер `services.auth` исчез вместе с
удалением `tests/unit/test_totp.py`, E5 закрыта как потерявшая предмет.

## Режим исполнения

Hermes может делегировать субагентам разбор отдельных падающих файлов — по одному файлу на
субагента, области не пересекаются. За оркестратором остаются: переход job на каталог,
решение по каждому падению и полный прогон на совмещённой ветке.

## Проблема

Job `python` запускает **поимённый список** файлов:

```yaml
python -m pytest
  services/reasoning-engine/tests/unit
  services/pipeline/tests/unit
  tests/unit/test_measurability.py
  tests/unit/test_eval_suite.py
  tests/unit/test_drift_check.py
  tests/unit/test_roadmap_guard.py
  tests/unit/test_event_streaming.py
  tests/unit/test_pipeline_events.py
  tests/unit/test_ci_evidence.py
```

В каталоге `tests/unit` четырнадцать файлов. Часть в список не входит и, соответственно, не
проверяется никогда.

**Один из них падает прямо сейчас на `main`:**

```
tests/unit/test_pipeline.py::test_planner_returns_steps
TypeError: Planner.plan() missing 3 required positional arguments:
           'task_description', 'client', and 'reasoning_url'
```

Планировщик изменил сигнатуру при подключении модельного цикла, тест остался прежним, и
никто этого не заметил, потому что файл не запускается. Сборка зелёная при сломанном тесте —
ровно та болезнь, с которой начинался весь наведённый порядок.

Поимённый список — не оптимизация, а способ не видеть. Каждый новый набор тестов по
умолчанию оказывается невидимым, пока кто-то не вспомнит дописать строчку.

## Что сделать

### 1. Перевести на каталоги

Job запускает `tests/unit` целиком и оба каталога тестов внутри сервисов. Никаких
перечислений файлов. То же для `ruff`.

Если какой-то файл действительно нельзя запускать в этом окружении — исключение объявляется
в конфигурации pytest с комментарием о причине, а не умолчанием в списке job.

### 2. Разобрать всё, что всплывёт

Ожидаемо упадёт несколько файлов. По каждому — решение, а не подгонка:

- **тест устарел вслед за кодом** (случай `test_pipeline.py`): привести к текущей сигнатуре,
  сохранив смысл проверки. Заглушки делать нестрогими, чтобы следующая смена сигнатуры
  падала на утверждении, а не на вызове;
- **тест нашёл настоящий дефект**: не чинить тест. Зафиксировать падающим, описать дефект,
  завести отдельную задачу и сообщить;
- **тест бессмыслен** (проверяет удалённое): удалить, объяснив в отчёте, что именно ушло и
  почему это не потеря покрытия.

Существующие утверждения не ослаблять. Пропуски и `xfail` не использовать как способ
позеленить сборку.

### 3. Защита от повторения

Добавить проверку: список файлов, запускаемых в CI, не расходится с содержимым каталогов
тестов. Реализуй тем способом, который надёжен в вашем CI — достаточно того, чтобы
появление нового файла тестов не проходило мимо прогона.

## Критерий приёмки

```bash
python -m pytest tests/unit services/reasoning-engine/tests/unit services/pipeline/tests/unit -q
ruff check services scripts tests
python scripts/drift_check.py
```

- job `python` запускает каталоги, а не список файлов;
- все четырнадцать файлов в `tests/unit` выполняются;
- `test_planner_returns_steps` проходит либо зафиксирован как найденный дефект с отдельной
  задачей;
- по каждому разобранному падению в отчёте сказано, к какой из трёх категорий оно отнесено;
- новый файл тестов, добавленный временно, попадает в прогон — показать демонстрацией;
- ссылка на зелёный прогон.

## Границы

`.github/workflows/ci.yml`, конфигурация pytest, файлы тестов, которые потребуют правки.
Продуктовый код не менять: если тест вскрыл дефект — это находка, а не помеха.
