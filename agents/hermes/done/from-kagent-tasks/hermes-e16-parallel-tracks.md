# E16 — три параллельные линии разработки

Правила — `AGENTS.md`. Это план распараллеливания программы `hermes-e14`, а не отдельная
задача.

## Топология

Hermes — единственный оркестратор. Три кодера работают одновременно, каждый в своей ветке от
свежего `origin/main`, каждый сдаёт свой pull request.

Оркестратор не пишет код в линиях. Его работа: выдать области, разрешить конфликты, свести
результаты, прогнать полный критерий на `main` после каждого слияния.

## Что делает параллельную работу возможной

Три линии выбраны так, чтобы **не пересекаться по файлам**. Это единственное, что защищает от
повторения истории B4/B5, где две задачи независимо переписали один файл и одну работу
выбросили целиком.

| Линия | Область файлов — исключительная | Предмет |
|---|---|---|
| **A. Экономика** | `services/reasoning-engine/src/**` | двухфазный бюджетный ledger, затем кэш модельных вызовов |
| **B. Целостность верификации** | `scripts/**`, `.github/workflows/ci.yml` | разделение code diff и test diff, запрет подмены проверок, мутационная проверка |
| **C. Взаимодействие** | `services/pipeline/src/**`, `services/control-plane/src/**` | контракт человеческого решения с TTL, освобождение исполнителя на время ожидания |

Кодер не открывает файлы вне своей области. Нашёл там дефект — пишет оркестратору, не чинит.

## Зарезервировано за оркестратором

Эти файлы конфликтуют всегда, потому что в них дописывают все:

```
docs/adr/README.md          docs/capabilities.json
CHANGELOG.md                docs/ROADMAP.md
AGENT_CHANGELOG.md          migrations/ — нумерация
```

Кодер **не редактирует их сам**. Он присылает оркестратору текст своей записи, оркестратор
вносит при сведении. Отдельный ADR своей линии кодер пишет — но номер получает заранее, см.
ниже.

## Номера выдаются до начала работы

Оркестратор распределяет **сейчас**, до первого коммита, и сообщает каждому:

- номер ADR для линии A, B, C;
- номер миграции для линий, которым нужна схема (A — бюджет, C — очередь решений).

Причина: коллизия номеров ADR случалась в этом проекте четыре раза подряд, и каждый раз её
разбирали вручную при слиянии. Выданный заранее номер стоит одну строку в задании.

## Порядок слияния

Линии независимы, но сливаются по очереди — иначе `main` меняется под ногами у двух
остальных:

1. кто первым дошёл до зелёного, тот сливается первым;
2. остальные немедленно перебазируются на новый `main` и перепрогоняют — верификация на
   устаревшей базе права на слияние не даёт;
3. если после перебазирования прогон красный, чинит владелец линии, а не оркестратор.

## Перекрёстное ревью

Три кодера — впервые появилась возможность выполнять правило «проверяет не автор» по-настоящему:

- линию A ревьюит кодер линии B;
- линию B — кодер линии C;
- линию C — кодер линии A.

Ревьюер получает полный текст постановки и `AGENTS.md`, работает только на чтение, ничего не
коммитит. Его вывод — список замечаний со ссылками на файлы и строки. Утверждение без ссылки
замечанием не считается.

Оркестратор не заменяет ревью своим мнением, но решает, что из замечаний блокирует слияние.

## Линия A — экономика

Подробная постановка: `hermes-e15-budget-ledger-and-cache.md`. Два pull request внутри
линии: сначала ledger, потом кэш.

Это самая сложная линия по существу: атомарность резервирования проверяется только под
параллельной нагрузкой. **Отдай её сильнейшему кодеру.** По наблюдаемой истории это
Antigravity: песочница на bubblewrap, TOTP с векторами RFC и адаптер PostgreSQL — его работа.

## Линия B — целостность верификации

Реализует ADR-0005 и ADR-0009, этап 0.9.3. Режется минимум на три pull request:

1. **разделение диффов**: изменения кода и изменения тестов различимы при просмотре; список
   тестовых путей задачи фиксируется до начала реализации и попадает в `forbidden_paths`;
2. **запрет подмены проверки**: сканирование test diff на пропуски, ожидаемые падения, пустые
   обработчики исключений, ослабленные утверждения, снижение порогов, флаги обхода. Совпадение
   блокирует завершение и не снимается самим исполнителем;
3. **мутационная проверка**: в изменённый код вносится ограниченный набор синтетических
   дефектов, новые тесты обязаны их обнаружить. `mutation_score` фиксируется как метрика
   готовности.

Merge queue из ADR-0009 — отдельным шагом после этих трёх, он меняет процесс слияния.

Проверка обязана падать на подложном изменении: продемонстрируй pull request, где тест
помечен пропущенным, и покажи красный прогон.

## Линия C — контракт человеческого решения

Реализует ADR-0011, часть этапа 0.9.5.

- типизированный объект вопроса: идентификатор, запуск, задача, вид, срочность, формулировка,
  варианты, значение по умолчанию, TTL, поведение при истечении, доказательства, каналы;
- постановка вопроса **освобождает исполнителя и снимает бюджетный резерв** после контрольной
  точки. Это стык с линией A: пока её ledger не влит, сними резерв заглушкой и оставь
  отметку в отчёте;
- контекст возобновления в контрольной точке, а не в памяти процесса;
- `assume_default` допустим только при объявленном значении по умолчанию и обратимом
  действии; необратимые используют `park` или `abort`;
- единая очередь решений по всем проектам, вопрос уровня `blocking` с истёкшим TTL порождает
  инцидент;
- ответ пишется в audit log с идентичностью ответившего.

## Правила, общие для всех трёх

- шаг обязан помещаться в один заход; не помещается — режь дальше;
- существующие тесты не изменять;
- статусы ADR не трогать: их ставит владелец;
- секреты не появляются в логах, ответах и тексте ошибок;
- тесты не обращаются к платному поставщику;
- после каждого слияния — короткий отчёт оркестратора: что влито, ссылка на прогон, что
  осталось.

## Критерий приёмки

- три линии влиты отдельными pull request, каждая со своим зелёным прогоном;
- ни одного конфликта в зарезервированных файлах — записи вносил оркестратор;
- ни одной коллизии номеров ADR и миграций;
- перекрёстное ревью выполнено, замечания приложены со ссылками;
- нагрузочный тест линии A, демонстрация подложного изменения линии B и сценарий ожидания
  линии C приведены выводом;
- возможности в `docs/capabilities.json` ссылаются на новые доказательства.
