**Исполнитель: Hermes**

# E14 — программа: довести отложенные этапы 0.9.2–0.9.5

Правила — `AGENTS.md`. Это **программа**, а не одна задача: ветка на каждый шаг, свой pull
request, свой зелёный прогон.

## Почему программа, а не задание

Эти этапы уже дважды пытались выполнить одной карточкой. Оба раза прогон упирался в бюджет
итераций и не давал ничего — ни кода, ни отчёта. Постановки лежат в `Отложенные/`.

Причина не в исполнителе, а в размере. Здесь ты работаешь **оркестратором программы**: сам
режешь этапы на шаги, сам ведёшь очередь, сдаёшь по одному.

## Незыблемые правила

1. **Один шаг — одна ветка от свежего `origin/main` — один pull request — зелёный прогон.**
   Ветка на несколько шагов запрещена, даже если шаги мелкие;
2. **шаг обязан помещаться в один заход.** Не помещается — режь дальше. Признак правильного
   размера: один-два файла и одна проверочная команда;
3. **не начинать следующий шаг, пока предыдущий не влит.** Внутри шага субагенты работают
   параллельно, между шагами — нет;
4. **при исчерпании бюджета** доводи текущий шаг до фиксации, описывай остаток и
   останавливайся;
5. **после каждого шага** — короткий отчёт: что влито, ссылка на прогон, что осталось.

## Что уже сделано — не переделывать

Проверено по коду в `main` на 2026-08-12:

- кассеты и режимы `live` / `record` / `replay` — ADR-0026;
- пул аккаунтов поставщиков с арендой — ADR-0032;
- ledger эффектов для git-операций — ADR-0028, частично;
- полный Python-suite, вычисляемый статус, публикация в ветку `verification-state`,
  список дрейфа, гейт сборки семи образов, подъём compose и сценарий через Gateway,
  три наполненных случая оценки, продакшн-развёртывание с TLS и резервным копированием.

Шаги 1–3 прежней редакции этой программы закрыты. Осталось четыре.

## Порядок

### Шаг 1 — `hermes-e15-budget-ledger-and-cache.md`

Готовая постановка, два pull request внутри: двухфазный бюджетный ledger, затем кэш
модельных вызовов. Закрывает этап 0.9.4.

Первым делом именно это: пул аккаунтов влит, параллелизм вырос, а расход не ограничен ничем,
кроме лимита на отдельный запрос.

### Шаг 2 — 0.9.3, целостность верификации

Самый крупный этап, режь минимум на три pull request:

- разделение code diff и test diff, заморозка тестов на время реализации;
- проверка запрещённых конструкций в test diff: пропуски, ожидаемые падения, пустые
  обработчики исключений, ослабленные утверждения;
- мутационная проверка новых тестов и учёт `escape_defects`.

Merge queue из ADR-0009 — отдельным шагом в конец: он меняет процесс слияния, включать его
стоит, когда остальное работает.

### Шаг 3 — остаток 0.9.2: реестр промптов и жизненный цикл контекста

- реестр промптов с версиями и содержимым в трекаемых файлах, ADR-0007. Runtime резолвит
  только через реестр, инлайн-литералы запрещены проверкой. Кэш из шага 1 уже содержит поле
  под версию промпта — заполнить его здесь;
- жизненный цикл контекста, ADR-0012: бюджет на роль, якоря, механика реза при
  компактификации, метки происхождения. Механика описана в решении подробно — следуй ей.

### Шаг 4 — 0.9.5, взаимодействие и границы

- контракт человеческого решения с TTL и политикой на таймаут, ADR-0011. Ожидающая задача
  освобождает исполнителя и не держит бюджетный резерв — это связано с шагом 1;
- исполняемые уроки, ADR-0014: урок становится действующим, только если объявляет, как
  меняет поведение;
- изоляция личного контура, ADR-0015: разработческие роли не адресуют личные данные
  конструктивно, а не по политике.

## Что не входит

- ADR-0017, программная среда с единственным инструментом: отложен владельцем;
- задачи Antigravity;
- наполнение набора оценки сверх трёх готовых случаев.

## Критерий приёмки программы

- все шаги влиты отдельными pull request, каждый со своим зелёным прогоном;
- решения ADR-0006, 0007, 0009, 0011, 0012, 0013, 0014, 0015 имеют работающую реализацию,
  а не только текст;
- соответствующие возможности в `docs/capabilities.json` ссылаются на доказательства и
  перестают быть `unverified`;
- в `Отложенные/` не остаётся ни одной постановки.

Программа не считается выполненной по сумме отчётов — только по влитым изменениям и зелёным
прогонам.
