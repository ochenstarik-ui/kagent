# ADR 0024: Real Model Execution and Testing

## Status
Proposed

## Context

Ранее `/v1/execute` в `Reasoning Engine` был заглушкой. Для работы платформы необходимо фактическое исполнение моделей, выбранных на этапе `/v1/decide`. При этом тесты не должны зависеть от реальных провайдеров (для стабильности, экономии средств и независимости от сети), но должны проверять логику отказоустойчивости (fallback) и вычисления стоимости.

## Decision

1.  **Двухэтапность и State**: Решение из `/v1/decide` временно кэшируется (TTL) в памяти `server.py` по `request_id`, чтобы `/v1/execute` мог извлечь контекст выбранной и запасных моделей, не передавая это состояние через клиента.
2.  **Fallback**: При сетевой ошибке или ошибке провайдера (5xx) движок пытается вызвать следующую модель из `fallback_models`. При исчерпании списка возвращается ошибка. Каждая попытка (и успешная, и неудачная) записывается в телеметрию с отсечением секретных ключей из текста ошибки.
3.  **Cassettes (ADR-0004)**: Для тестирования реализованы режимы `live`, `record`, и `replay` (через переменную окружения `EXECUTION_MODE`).
    *   `record`: Успешные ответы провайдеров записываются в файлы `cassettes/{request_id}_{hash}.json`.
    *   `replay`: Вместо сетевого вызова читается содержимое кассеты. Если её нет, возвращается ошибка.
4.  **Unit Tests**: Написаны изолированные тесты, использующие `AsyncMock` и `pytest` для симуляции сети, без расхода реальных токенов.

## Consequences

*   **Positive**: Безопасная и экономичная база для тестирования LLM-интеграций; устойчивость пайплайна к кратковременным сбоям провайдеров; готовность P1.
*   **Negative**: Временный in-memory кэш решений не переживёт рестарт сервиса, но для эфемерного движка это приемлемо (при сбое клиент просто пересоздаст запрос).
